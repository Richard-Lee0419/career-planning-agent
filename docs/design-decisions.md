# 当前实现的设计取舍

本文解释 B 方案优化后的实现，不把代码推断写成作者过去的开发动机。本轮选择与范围有[优化计划](optimization-plan.md)、[来源记录](data-sources.md)和对应代码支持；此前未记录的选择仍需作者结合真实经历说明。测试结果和外部服务实际运行状态见[验证记录](validation.md)。

## 1. 先整理六个入门角色，区分标准与招聘样本

**当前方案与证据。** [试点数据包](../data/pilot_job_standards.json)维护两个领域、六个角色、任务、能力及公开来源；[导入脚本](../scripts/seed_pilot_standards.py)仅新增缺失标准。`jobs` 用于岗位浏览/统计，`job_standard_profiles` 用于覆盖计算；两者没有自动转换关系。

**解决的问题。** 原标准偏技术方向，一周演示预算内需要完成少量非技术角色的完整流程，并让外部访问者能核对能力要求的依据。本轮任务摘要以中国资料为主，教学标准和雇主任务例证分开标注。

**替代方案。** 可直接导入完整职业目录，翻译 ESCO/O*NET，或建立多行业招聘语料统计管线。目录通常没有可评分能力，海外资料需要地区复核；语料管线还需要可用数据、来源权利、日期和去重规则。它们均不能靠增加角色名称完成。

**成本与边界。** 人工维护扩展较慢，六项核心能力是本轮控制粒度的选择，不是官方统一标准。`source_checked` 只表示资料核对；尚无从业者评审或推荐效果评估。人事和培训角色的直接雇主例证仍不足。本轮资料不支持全专业映射、需求频率或薪资结论。

**记录支持。** 有本轮 B 方案计划及逐角色来源/限制记录；没有证据把当前方式追认为原企业数据清洗时的设计。若继续扩展，优先补来源及样本处理管线，再增加角色数量。

## 2. 用小词典计算覆盖，模型解释差距和建议

**当前方案与证据。** [core/matching.py](../core/matching.py)统一规范化和评分，试点包维护项目技能 ID 及明确别名。默认权重是核心能力 80%、软素质 15%、目标或兴趣 5%；软素质要求缺失时重新归一化。`main.py` 的 `scored_standard` 附加来源状态，拒绝给修改后未核对或未分类标准当前分数。模型负责提取、解释、路径和问答。

**解决的问题。** 同一能力的名称变体会造成假差距；用模型直接给综合分数则难以稳定复现。规则可以追溯命中和缺失项，推荐、差距和报告共用依据。兴趣允许相关关键词判断，但不被当成能力证据。

**替代方案。** 嵌入相似度、LLM 判断技能或训练中文抽取模型可以处理自由文本，但需要独立标注样本、阈值及误差评价，才能确认没有把相邻知识误认成能力。

**成本与边界。** 小词典容易解释和测试，也会漏掉未登记的同义词。宽泛“Office”不代表掌握某个业务流程，学习计划不代表掌握技能。能力来自用户自述；权重未经就业效果校准，包含偏好的加权参考不能当作纯技能测量或跨职业统一适合度。`domain` 可过滤推荐；接口仍允许省略领域返回全部标准，调用者必须保留比较范围提示。

**记录支持。** 本轮明确别名与匹配错误有回归测试支持；不能称为经实验证明优于语义模型。需处理更多自由文本时，应先建设抽取评价集，再比较方法，而非直接替换可解释规则。

## 3. 来源元数据与内容指纹独立存储，历史保存快照

**当前方案与证据。** [模型](../models/db_models.py)新增 `DBJobStandardMetadata`，不改旧标准列。[core/standards.py](../core/standards.py)校验来源、领域和技能映射，并保存岗位名称、说明及能力要求的指纹。`standard_metadata` 检出偏离时返回 `modified_unverified`，保留原来源但停止沿用旧核对状态。路径保存画像、匹配和来源快照；恢复及导出读取所选旧版本，不用当前目录替代旧证据。

**解决的问题。** 新来源不能虚套到已有同名旧标准；后续修改标准也不能让旧路径看起来依据的是最新资料。来源身份、当前内容和生成时依据因此需要分别保留。

**替代方案。** 可以直接给旧表加大量来源列，历史只存标准外键，或建立完整标准版本表。只存外键会让历史解释随标准变化；完整版本模型更适合频繁发布和审阅，但本轮维护成本较高。

**成本与边界。** 附加表保持兼容，但会增加读取查询。同名角色不覆盖，因此重复种子导入不是版本升级工具；重新审核和版本迁移仍需明确流程。指纹只能发现内容偏离，不能证明来源可靠或防止有数据库写权限的人同时改内容与指纹。早期路径没有来源时继续显示缺失，无法补造历史。

**记录支持。** 来源状态、同名碰撞、改动失效和快照保留有本轮代码及回归。它们证明工程边界得到保护，不证明职业标准内容经过专家审核。后续多版本维护时可增加标准版本表和显式审核操作。

## 4. 保留 SQLite，把慢模型调用与持久化分开

**当前方案与证据。** [core/database.py](../core/database.py)使用 SQLite、每请求 Session 和 `autoflush=False`，支持 `CAREER_DATABASE_PATH` 隔离演示。`career_chat` 在 AI 返回后只刷新会话关闭标志，保留尚未提交的岗位/路径绑定，不在慢调用前 flush；结果提交前再次检查会话关闭。数据库唯一索引参与重试幂等保护。

**解决的问题。** 本地运行无需外部数据库。慢 AI 请求期间不应提前拿 SQLite 写锁；完整刷新又会丢弃未 flush 的会话关联，所以刷新范围需要明确。

**替代方案。** PostgreSQL 更适合较多并发写入和复杂查询；多实例限流可用共享存储，耗时任务也可增加任务队列。当前没有通过实测用户负载证明必须采用这些组件。

**成本与边界。** SQLite 单写者及单进程限流适合本地、单实例演示，不构成高并发能力承诺。当前回归覆盖“AI 期间另一次清空请求能够提交、晚到回答不存消息”，没有压力测试所有竞态。旧 Excel 导入脚本仍用固定路径，不受演示数据库变量控制，运行前需要单独核对。

**记录支持。** SQLite 选择发生在本轮之前，未见其原始决策记录；隔离路径及会话刷新修补有当前实现、复现记录和回归支持。出现持续并发写入、共享限流或后台任务需求时，再评估迁移。

## 5. 以规则和真实 HTTP 回归保护边界，单独记录真实服务演示

真实演示发现“模型评审通过”仍会产生无来源认证或笼统任务，所以非 IT 试点另校验动作、产出、自查、耗时和最多四周的时间预算，并过滤未核对资源；模型的资源对象与字符串先归一到来源标签。这比只加提示词多一层失败保护，也提高了弱模型返回失败的可能。结构和估时通过不等于内容适用；本轮不做静默模板替换或隐瞒失败。

**当前方案与证据。** [后端测试](../tests/)分为匹配、来源导入及 HTTP 流程，使用真实 SQLAlchemy/隔离 SQLite，只替换外部 AI；两领域覆盖问卷、差距、路径、进度、恢复、聊天和导出。已校验的画像、路径及面试错误结构不落库、跨用户访问、限流状态隔离、来源快照和长上下文压缩也受保护。前端使用 Node 逻辑测试、类型检查、lint 与构建；[CI](../.github/workflows/ci.yml)配置这些检查。

**解决的问题。** 外部模型响应变化、费用和网络失败不应阻碍保存/权限/数据流的稳定回归。可控响应能构造异常，真实数据库和 HTTP 路由能验证集成，而不是只验证函数可调用。

**替代方案。** 每次测试调用真实模型会引入费用和不稳定输出；完全 mock 数据库则容易漏掉保存和重新加载问题。浏览器端到端测试可以继续保护交互，真实模型验收需要单独运行。

**成本与边界。** 可控模型不评价真实输出质量；前端辅助函数测试不保证页面点击正确。真实模型连通、浏览器贯通、来源可信度和就业效果是不同证据，不能互相替代。远程执行结果见仓库Actions，实际本地结果记录在[验证记录](validation.md)。

**记录支持。** 当前测试和验证记录支持上述边界，未证明原作者过去采用相同测试策略。下一步应根据真实失败补少量回归，并以可复现演示记录补齐服务和界面证据；不按测试数量包装质量。

2026-10-12后续修正：入门计划只选标准顺序中的前两项未匹配能力，不把此顺序解释为职业重要性；没有缺口时允许深化已有能力，信息不足时明确探索性质。任务必须标明目标能力，最多进行一次受校验的修正，避免无限重试。顾问在上下文压缩前计算所选版本的首项待办，压缩后保留它，避免只看到部分完成记录就跨阶段。两轮起草与评审是模型工作流，不是强化学习的Actor-Critic算法；应用层调用次数也不等于SDK内部请求次数。具体成功与局限见[六角色内容评审](demo/release-evaluation.md)。
